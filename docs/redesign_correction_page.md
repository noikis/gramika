# Gramika — Редизайн страницы Correction

> **Финальные решения для реализации (2026-11-04).**
> Эти решения имеют приоритет над ранними формулировками ниже и деталями макетов.
>
> 1. **TextDiff не менять вообще**: отдельный пакет `packages/text-diff`,
>    его алгоритм, UI и существующую frontend-интеграцию. Использовать
>    оригинальную подсветку и переключатель «Текст / Изменения». По умолчанию
>    после проверки включены «Изменения».
> 2. **Header, логотип и глобальную навигацию не менять**. На AI-макетах
>    изображена иная версия; настоящая остаётся как в приложении.
> 3. Сохранить **RU / EN / FR**. Русский на скриншотах - выбранная локаль.
>    Все новые строки локализовать.
> 4. Менять **только мобильную Correction**. Desktop-редизайн отложен.
>    Не менять backend, промпты, API, настройки моделей и другие страницы.
> 5. До проверки: «+ Новый текст», «Вставить», «Озвучить», «Перевести».
>    **Словарь для всего исходного текста не показывать**. После проверки
>    исходный textarea компактный, **без всех action-иконок**.
> 6. Между текстом и результатом тонкий **серый** разделитель
>    «Результат 1 из 1 · Строгий»; при нескольких вариантах - стрелки и
>    «Вариант 2 из 3 · Переписывание». Без зелёного «Исправлено»,
>    крупного заголовка «Исправленный текст» и точек пагинации.
> 7. Карточка результата выводит оригинальный TextDiff,
>    «Озвучить» слева внизу, существующий «Текст / Изменения» справа.
>    Ниже - «Исправления (N)», «Скопировать», «+ Ещё вариант».
> 8. «Ещё вариант» открывает просторный bottom sheet с двумя
>    пунктами Strict/Rewrite. **Нажатие на пункт сразу запускает запрос**.
>    Отдельной кнопки «Создать вариант» и выбора модели нет.
>    Предыдущие варианты сохраняются, режимы могут различаться.
> 9. «Исправления (N)» открывает bottom sheet: нейтральные нумерованные
>    строки «ошибка → исправление» с переносами, справа
>    **четырёхлучевая звезда + «Объяснить»**. Без «Было / Стало».
> 10. Contextual popover показывает **только применимые действия**:
>     словарь - для одного слова, перевод - для слова или фразы,
>     Explain - для однозначно связанного исправления.
> 11. Explain - **простой компактный** bottom sheet из финального макета 8:
>     заголовок, строка изменения со стрелкой, абзац объяснения, «Готово».
>     Не открывать второй drawer поверх первого.
> 12. Финальные референсы: `prototypes/correction_redesign/` (1-8 и 9-A/9-B).
>     Макета «нет исправлений» нет; сохранить существующее поведение.


**Статус:** согласованное UX-ТЗ  
**Область:** только frontend страницы Correction  
**Репозиторий:** https://github.com/noikis/gramika  
**Приоритет:** сохранение функциональности, удобство использования, мобильная версия

## 1. Цель

Полностью переработать UI/UX страницы Correction приложения Gramika, сохранив существующую функциональность.

Основные проблемы текущего интерфейса:

1. Пользователям сложно обнаруживать дополнительные функции.
2. Пользователи теряются при переходах между коррекцией, словарём, переводом и объяснениями.
3. Недостаточно удобно взаимодействовать с исправленными словами и выражениями.
4. Управление несколькими результатами коррекции требует улучшения.
5. Интерфейс должен эффективнее использовать пространство мобильного экрана.

Новый интерфейс должен быть:

- Mobile-first.
- Интуитивным для пользователей без технических знаний.
- Минималистичным, но функциональным.
- Визуально последовательным.
- Удобным для работы с короткими и длинными текстами.
- Совместимым с существующими функциями приложения.

### Главный принцип

**Изменять способ взаимодействия с функциональностью, но не саму функциональность.**

Это редизайн frontend, а не переписывание бизнес-логики приложения.

## 2. Источники требований и их приоритет

При реализации использовать три источника.

### 2.1. Существующий код

Код приложения является источником истины относительно:

- Существующих API.
- Форматов запросов и ответов.
- Режимов коррекции.
- Логики генерации результатов.
- Истории.
- Сохранения состояния.
- Dictionary, Translation, Explain и TTS.
- Обработки ошибок.
- Существующих ограничений.

Не изменять эти контракты без необходимости.

### 2.2. Данное ТЗ

Этот документ является источником истины относительно нового UX.

Если поведение на макете противоречит ТЗ, следовать ТЗ.

### 2.3. Визуальные макеты

Макеты используются для:

- Композиции.
- Расположения элементов.
- Визуальной иерархии.
- Пропорций.
- Взаимодействий.
- Адаптивного дизайна.

Макеты не являются точной технической спецификацией.

Некоторые ранние макеты содержат устаревшие решения:

- Выбор LLM-модели.
- Отдельный крупный бейдж Strict.
- Точки переключения результатов.
- Другую цветовую гамму.
- Неполные или условные примеры исправлений.

Не переносить эти решения в окончательную реализацию.

### Приоритет

1. Существующие функциональные контракты.
2. Согласованные UX-требования этого документа.
3. Последние актуальные макеты.
4. Ранние макеты — только как вспомогательные визуальные примеры.

Если требования противоречат существующей архитектуре или друг другу, остановиться и сообщить о противоречии. Не принимать молча продуктовые решения.

## 3. Границы задачи

### Входит в задачу

- Страница Correction.
- Редактор исходного текста в пределах необходимых изменений.
- Отображение результатов коррекции.
- Несколько вариантов результата.
- Переключение вариантов.
- Создание дополнительного варианта.
- Выделение текста.
- Контекстное меню действий.
- Список исправлений.
- Отображение Explain.
- Вызов существующих Dictionary и Translation из Correction.
- Адаптивность.
- Доступность.
- Тестирование изменённых сценариев.

### Не входит в задачу

- Редизайн самостоятельных страниц Dictionary и Translation.
- Редизайн History.
- Редизайн Settings.
- Полная замена глобальной навигации приложения.
- Изменение backend.
- Изменение промптов коррекции.
- Изменение провайдера LLM.
- Изменение API-контрактов.
- Новые функции обучения, упражнения или карточки слов.
- Новые возможности словаря или перевода.
- Монетизация.
- Система тарифов.
- Выбор LLM-модели пользователем.

Если существующий глобальный компонент используется несколькими страницами, изменения должны сохранять поведение остальных страниц.

**Не реализовывать новую глобальную bottom navigation только потому, что она присутствует на концептуальных макетах.** Это отдельная задача будущего редизайна приложения.

## 4. Визуальная система

### 4.1. Сохранение идентичности

Использовать существующую визуальную идентичность Gramika:

- Текущий логотип.
- Текущую зелёную палитру.
- Тёплые фоновые оттенки.
- Поддержку существующих тем.
- Существующие дизайн-токены, где они доступны.

Цвета с AI-макетов не являются эталоном.

Не вводить новую палитру только ради соответствия изображениям.

### 4.2. Общий стиль

Ориентироваться на:

- Чистую композицию.
- Достаточные отступы.
- Хорошую читаемость русского текста.
- Мягкие скругления.
- Умеренные границы и тени.
- Компактные элементы управления.
- Минимальное количество декоративных элементов.

Главный визуальный элемент страницы — текст.

Кнопки, индикаторы и метаданные не должны конкурировать с ним за внимание.

### 4.3. Технологические ограничения

Сохранять существующий frontend-стек.

- Использовать Tailwind CSS.
- Переиспользовать существующие UI-компоненты, где возможно.
- Не внедрять SCSS или CSS-in-JS.
- Не добавлять новые библиотеки без конкретного обоснования.
- Не создавать новый глобальный state manager без необходимости.
- Использовать существующую архитектуру состояния и запросов.

## 5. Страница Correction

### 5.1. Начальное состояние

При открытии Gramika пользователь попадает на Correction.

Должны оставаться доступны:

- Ввод исходного текста.
- Вставка текста.
- Выбор режима.
- Запуск коррекции.
- Существующие действия редактора.
- Существующие ограничения ввода.
- Существующие ошибки и состояния загрузки.

Поведение редактируемого поля не менять.

Нажатие на текст в редакторе должно устанавливать курсор. Не открывать контекстное меню слов по обычному нажатию внутри редактора.

### 5.2. Запуск коррекции

Сохранить существующие режимы:

- `Strict`
- `Rewrite`

Сохранить существующую логику отправки запроса.

Коррекция запускается только явно пользователем.

Не добавлять автоматических повторов запросов.

Не менять правила, параметры или модели коррекции.

### 5.3. Состояние выполнения

Во время запроса:

- Показывать понятный индикатор загрузки.
- Предотвращать случайную повторную отправку того же действия.
- Сохранять исходный текст.
- Не показывать фиктивный результат.
- Не разрушать текущие сохранённые результаты при ошибке.

Сохранить существующую обработку ошибок, включая ошибки провайдера и недоступность модели.

## 6. Экран результата коррекции

После успешной коррекции отображать:

1. Исходный текст.
2. Статус завершения.
3. Активный результат.
4. Подсветку исправлений.
5. Управление вариантами.
6. Список исправлений.
7. Действия с результатом.

### 6.1. Исходный текст

Исходный текст остаётся доступным для просмотра.

До проверки в редакторе показываются общетекстовые TTS и перевод.
После получения результата нижняя панель действий исходного текста скрывается.
Сами функции TTS, Dictionary и Translation остаются доступны в применимых контекстах.

Добавить понятное действие:

**«Новый текст»**

Оно означает начало работы с другим исходным текстом.

Не смешивать его с созданием дополнительного результата для текущего текста.

Нельзя незаметно уничтожать существующие результаты или несохранённые данные.

Конкретную реализацию очистки и восстановления состояния согласовать с текущей логикой истории приложения.

### 6.2. Карточка результата

Использовать композицию согласованного макета:

- Светлая карточка.
- Хорошо читаемый текст.
- Подсветка исправлений.
- Минимум вспомогательных элементов.
- Адаптивная высота.

**Не задавать карточке большую фиксированную высоту.**

Размер определяется содержимым.

Для длинного текста страница должна прокручиваться естественным образом.

### 6.3. Основные действия

Под результатом:

- «Скопировать».
- «Ещё вариант».

Не использовать длинную подпись «Скопировать результат».

Копирование должно относиться к активному варианту.

После копирования показывать существующую обратную связь или подходящее краткое подтверждение.

## 7. Несколько результатов коррекции

### 7.1. Общая модель

Один исходный текст может иметь несколько результатов.

Все результаты одной группы относятся к одному и тому же исходному тексту.

Каждый результат имеет:

- Стабильный идентификатор в рамках текущей реализации.
- Позицию в последовательности вариантов.
- Режим `Strict` или `Rewrite`.
- Собственный исправленный текст.
- Собственные изменения.
- Собственные связанные объяснения, если они поддерживаются текущей моделью данных.

Не смешивать результаты разных исходных текстов.

Если пользователь изменил исходный текст, нельзя незаметно добавить результат уже изменённого текста в старую группу вариантов.

### 7.2. Переключение результатов

На мобильном экране показывать один результат одновременно.

Разрешить:

- Переключение стрелками.
- Дополнительное переключение свайпом, если оно не мешает выделению текста.

Стрелки должны оставаться видимыми.

На первом и последнем варианте соответствующая стрелка должна быть неактивной.

Свайп не должен быть единственным способом навигации.

### 7.3. Компактный заголовок

Использовать одну строку:

**‹ Вариант 2 из 3 · Strict ›**

Требования:

- Номер текущего варианта.
- Общее количество вариантов.
- Режим активного варианта.
- Стрелки переключения.

Всё располагается в одной горизонтальной строке.

Не использовать:

- Отдельную строку для Strict/Rewrite.
- Крупные бейджи режима.
- Точки пагинации.
- Избыточные вертикальные отступы.

Режим показывать небольшим текстом без отдельного крупного контейнера.

### 7.4. Поведение переключения

При переключении меняются:

- Исправленный текст.
- Подсветка изменений.
- Список исправлений.
- Режим в заголовке.
- Связанные данные активного результата.

Исходный текст остаётся прежним.

Переключение не должно запускать новую коррекцию.

Желательно сохранять положение чтения. При различной длине вариантов допускается корректировка позиции до ближайшей допустимой области.

Не допускать резких скачков интерфейса без необходимости.

## 8. Создание нового варианта

### 8.1. Терминология

Разделить два действия:

**«Новый текст»**

Начать новую работу с другим текстом.

**«Ещё вариант»**

Создать дополнительный результат для того же исходного текста.

### 8.2. Открытие

Нажатие «Ещё вариант» открывает bottom sheet на мобильном устройстве.

Открытие панели само по себе не запускает запрос.

### 8.3. Содержимое панели

Заголовок:

**«Ещё вариант»**

Описание:

«Исходный текст и предыдущие результаты сохранятся».

Два варианта режима:

**Исправить ошибки — Strict**

Минимальные изменения, сохранение стиля и исходных формулировок.

**Переформулировать — Rewrite**

Более свободное изменение формулировок с сохранением смысла.

Каждый пункт режима является самостоятельной кнопкой.
Нажатие сразу запускает создание варианта без дополнительного подтверждения.

### 8.4. Выбор модели

Для обычного пользователя доступна только модель, настроенная приложением по умолчанию.

В интерфейсе не показывать:

- Выбор модели.
- Название модели.
- Стоимость токенов.
- Раздел экспериментальных моделей.
- Раскрываемые дополнительные настройки модели.
- Бейдж модели на карточке результата.

Выбор модели не является частью данного редизайна.

Не удалять техническую возможность конфигурирования модели из существующего приложения, если она используется внутренней логикой. Не создавать новый пользовательский интерфейс для неё.

### 8.5. Отправка

По нажатию на один из режимов:

1. Использовать тот же исходный текст.
2. Использовать выбранный режим.
3. Использовать стандартную модель.
4. Выполнить один запрос через существующую логику.
5. Сохранить предыдущие варианты.
6. После успеха добавить новый вариант.
7. Переключить активный результат на созданный вариант.

При ошибке:

- Сохранить существующие варианты.
- Показать ошибку.
- Позволить пользователю повторить действие вручную.
- Не выполнять автоматических повторных запросов.

Пока запрос выполняется, не допускать случайной повторной отправки.

## 9. Подсветка исправлений

### 9.1. Общие правила

Все исправления должны быть визуально различимы в тексте.

Использовать существующую систему diff как источник данных.

Не заменять её новой реализацией без необходимости.

Подсветка должна быть:

- Достаточно заметной.
- Не мешающей чтению.
- Совместимой с выделением текста.
- Корректной для длинных и многострочных фрагментов.

### 9.2. Несколько исправлений

Если исправлений несколько, каждое должно иметь собственную связь с соответствующим изменением.

Пример:

Исходный текст:

«Я незнаю, когда будет акредитация и кто придет».

Исправленный текст:

«Я не знаю, когда будет аккредитация и кто придёт».

Пример изменений:

1. `незнаю → не знаю`
2. `акредитация → аккредитация`
3. `придет → придёт`

Не отображать огромную отдельную карточку для каждого изменения непосредственно внутри результата.

### 9.3. Список исправлений

Под исправленным текстом предусмотреть раскрываемый раздел:

**«Исправления (N)»**

По умолчанию свёрнут. На мобильном нажатие открывает bottom sheet со списком.
У каждого исправления есть действие «✧ Объяснить» справа. Длинные фрагменты
переносятся, список прокручивается. Не показывать «Было» / «Стало».

Формат элемента:

`Исходный фрагмент → исправленный фрагмент`

Не добавлять избыточные пояснения непосредственно в список.

Например, не показывать автоматически «удвоенная „к“» под изменением `акредитация → аккредитация`.

Пояснение правила относится к Explain.

### 9.4. Связь списка и текста

Нажатие на изменение в списке:

- Находит соответствующий фрагмент в исправленном тексте.
- Подсвечивает его.
- При необходимости прокручивает к нему.
- Даёт возможность получить объяснение.

Если исправление связано только с пунктуацией или не имеет удобной области для нажатия в тексте, оно всё равно должно быть доступно из списка.

Количество исправлений должно определяться реальными данными, а не числом визуальных подсветок, если эти значения отличаются в существующей реализации.

## 10. Выделение текста

### 10.1. Область применения

Новая система контекстных действий применяется к read-only тексту результата коррекции.

Не вмешиваться в стандартное редактирование исходного текста.

### 10.2. Одно слово

При обычном нажатии на слово:

1. Выбрать слово.
2. Показать визуальное выделение.
3. Определить доступные действия.
4. Открыть contextual popover.

Пример: пользователь нажимает «знаю» внутри «не знаю».

Выбранный текст:

`знаю`

Действия:

- Словарь.
- Перевести.
- Объяснить исправление — если слово связано с конкретным исправлением.

### 10.3. Несколько слов

Пользователь может выделить выражение или произвольный фрагмент обычным механизмом выделения текста.

Для нескольких слов доступны:

- Перевести.
- Объяснить исправление, если выделение однозначно связано с одним исправлением.

Словарь не показывать.

### 10.4. Правила доступности действий

| Выделение                                      | Словарь | Перевести | Объяснить                        |
| ---------------------------------------------- | ------- | --------- | -------------------------------- |
| Одно поддерживаемое слово без исправления      | Да      | Да        | Нет                              |
| Одно слово внутри исправления                  | Да      | Да        | Да                               |
| Несколько слов без исправления                 | Нет     | Да        | Нет                              |
| Несколько слов, связанные с одним исправлением | Нет     | Да        | Да                               |
| Фрагмент, пересекающий несколько исправлений   | Нет     | Да        | Не выбирать ошибку автоматически |

Если выделение пересекает несколько ошибок и невозможно однозначно определить одну, действие Explain скрывается.

Объяснения отдельных ошибок остаются доступны через список исправлений.

### Главный принцип

**Показывать только применимые действия.**

Не отображать недоступные действия в виде неактивных кнопок.

### 10.5. Разделение контекстов

Технически различать:

**Selected text**

Фрагмент, который пользователь выделил.

Используется для словаря или перевода.

**Correction context**

Исправление, которому принадлежит выбранный фрагмент.

Используется для Explain.

Пример:

Выделено:

`знаю`

Связанное исправление:

`незнаю → не знаю`

Тогда:

- Словарь получает `знаю`.
- Перевод получает `знаю`.
- Explain получает контекст исправления `незнаю → не знаю`.

Не передавать в Explain произвольное выделенное слово вместо данных исправления.

Конкретный способ сопоставления исправлений определить после анализа существующего diff и формата результатов. `correctionId` здесь обозначает логическую связь, а не обязательное новое поле базы данных.

## 11. Contextual popover

### 11.1. Общий вид

Компактное всплывающее меню рядом с выделением.

Визуально ориентироваться на согласованные макеты.

Popover содержит:

- Выбранный текст.
- Применимые действия.
- При необходимости контекст исправления.
- Возможность закрытия.

### 11.2. Одно слово

Пример:

**Выбрано: знаю**

Действия:

- Словарь.
- Перевести.

Если слово связано с исправлением:

`незнаю → не знаю`

Дополнительно:

- Объяснить исправление.

Контекст должен быть визуально отделён от действий над словом.

### 11.3. Выражение

Пример:

**Выделено: не знаю**

Действия:

- Перевести выражение.
- Объяснить исправление.

Контекст:

`незнаю → не знаю`

Словарь отсутствует.

### 11.4. Позиционирование

Popover должен:

- Находиться рядом с выделением.
- Не закрывать выбранный фрагмент, если это возможно.
- Не выходить за границы экрана.
- Корректно работать при переносах строк.
- Учитывать размеры мобильного viewport.
- Перепозиционироваться при недостатке свободного пространства.
- Не перекрывать системную клавиатуру некорректным образом.

Точный вид указателя на AI-макетах не считать эталоном — на некоторых изображениях он расположен неточно.

### 11.5. Закрытие

Popover закрывается:

- По нажатию вне него.
- Через кнопку закрытия, если она предусмотрена.
- По Escape.
- При системной навигации назад, где применимо.

Сохранять корректную работу фокуса и выделения.

Не оставлять зависших popover после переключения результата.

### 11.6. API

Само выделение текста не вызывает Dictionary, Translation или Explain API.

Запрос выполняется только после явного выбора действия пользователем.

## 12. Dictionary и Translation

### 12.1. Dictionary

Dictionary принимает одно слово.

При выборе «Словарь»:

- Использовать существующую логику словаря.
- Передавать одно выбранное слово.
- Открывать существующее представление Dictionary.
- Не переделывать страницу словаря в рамках этого ТЗ.

Сохранить существующую обработку словоформ, отсутствующих слов и ошибок.

### 12.2. Translation

Translation поддерживает:

- Одно слово.
- Несколько слов.
- Выражение.
- Произвольный допустимый текстовый фрагмент.

При выборе «Перевести»:

- Передавать выбранный текст.
- Использовать существующую логику перевода.
- Открывать существующее представление Translation.
- Не переделывать страницу Translation.

### 12.3. Возвращение к Correction

При возвращении пользователь должен попадать в тот же контекст:

- Тот же исходный текст.
- Тот же активный вариант.
- Та же коррекция.
- По возможности та же позиция прокрутки.

Не терять результаты из-за перехода между инструментами.

Конкретный способ сохранения контекста выбирать с учётом текущей архитектуры маршрутизации и состояния приложения.

## 13. Explain

### 13.1. Назначение

Explain объясняет конкретное исправление.

Исправление может включать:

- Одно слово.
- Несколько слов.
- Пунктуацию.
- Другой фрагмент текста.

Explain не должен ошибочно считать, что исправление всегда равно одному слову.

### 13.2. Запуск

Explain доступен:

- Через contextual popover.
- Через соответствующий элемент списка исправлений.

Генерация происходит только по явному действию пользователя.

Не запускать объяснения автоматически:

- После коррекции.
- После выделения.
- После открытия popover.
- При переключении вариантов.
- При открытии drawer.

### 13.3. Мобильный интерфейс

Использовать bottom sheet.

Содержимое:

1. Заголовок «Объяснение».
2. Исходный фрагмент.
3. Исправленный фрагмент.
4. Текст объяснения.
5. Существующие необходимые действия.

Пример:

`незнаю → не знаю`

Объяснение правила отображается отдельным читаемым текстовым блоком.

### 13.4. Размеры

Bottom sheet:

- Открывается снизу и занимает естественную высоту короткого объяснения.
- Может расширяться при длинном содержимом до границы viewport.
- Поддерживает внутреннюю прокрутку.
- Не требует перехода на отдельную страницу.
- Не содержит дополнительных обязательных карточек правил.

Не допускать обрезания длинных объяснений.

### 13.5. Desktop

Desktop-редизайн отложен. Сохранить текущий desktop UI и отсутствие регрессий.

### 13.6. Состояния

Поддержать:

- Объяснение ещё не запрошено.
- Загрузка.
- Успешно полученное объяснение.
- Ранее сохранённое объяснение.
- Ошибка генерации.

Если объяснение уже сохранено, показывать его без повторного платного запроса.

Если текущая логика предусматривает отдельную явную регенерацию, сохранять её существующие ограничения. Не добавлять новую автоматическую регенерацию.

### 13.7. Закрытие

Закрытие через:

- Крестик.
- Свайп вниз на мобильном.
- Escape / системный Back.

После закрытия остаётся активен тот же результат и соответствующий контекст.

## 14. Работа с длинными текстами

- Короткий текст.
- Текст около 1 000 символов.
- Текст около 3 000 символов.
- Текст около 5 000 символов, если это поддерживаемый текущий лимит.

Требования:

- Не создавать горизонтальную прокрутку страницы.
- Не обрезать текст.
- Не перекрывать текст элементами навигации.
- Сохранять корректные позиции подсветки.
- Не делать длинный список исправлений постоянно раскрытым.
- Не создавать слишком большие отступы между элементами.
- Не терять состояние при переключении вариантов.

Особенно проверить работу выделения на границах строк и абзацев.

- Выделении слов.

## 18. План реализации

Работать строго по этапам.

После каждого этапа:

1. Проверить функциональность.
2. Запустить релевантные тесты.
3. Проверить отсутствие регрессий.
4. Показать результат и список изменённых файлов.
5. Дождаться подтверждения перед следующим этапом.

### Этап 0. Анализ

**Без изменения кода.**

Изучить:

- Текущую структуру Correction.
- Все состояния страницы.
- Логику результатов.
- Реализацию нескольких вариантов.
- Систему diff.
- Existing selection handling.
- Dictionary/Translation integration.
- Explain integration.
- Историю.
- Тесты.
- Стили.

Результат этапа:

- Краткая карта существующей архитектуры.
- Список переиспользуемых компонентов.
- Список необходимых изменений.
- Потенциальные риски.
- Несоответствия между ТЗ и текущей реализацией.

Если обнаружены блокирующие несоответствия — запросить решение до начала реализации.

### Этап 1. Карточка результата

Реализовать:

- Новую визуальную композицию.
- Адаптивную карточку.
- Подсветку.
- Компактный заголовок.
- Кнопки действий.

На этом этапе не изменять бизнес-логику запросов.

Критерий приёмки:

Существующий результат отображается в новом дизайне без потери функциональности.

### Этап 2. Варианты результата

Реализовать:

- Переключение вариантов.
- Компактный индикатор.
- Кнопку «Ещё вариант».
- Bottom sheet выбора Strict/Rewrite.
- Отдельное действие «Новый текст».
- Сохранение предыдущих результатов.

Не показывать выбор модели.

Критерий приёмки:

Пользователь может создать несколько результатов одного текста, переключаться между ними и видеть правильный режим каждого.

### Этап 3. Список исправлений

Реализовать:

- Раздел «Исправления (N)».
- Раскрытие и закрытие.
- Компактные элементы изменений.
- Связь каждого элемента с фрагментом текста.
- Прокрутку к выбранному исправлению.

Критерий приёмки:

Все изменения доступны для просмотра, включая пунктуационные исправления.

### Этап 4. Selection и popover

Реализовать:

- Выбор одного слова.
- Выделение нескольких слов.
- Контекстное меню.
- Правила доступности действий.
- Разделение selected text и correction context.
- Переходы в существующие Dictionary/Translation.
- Возврат в Correction с сохранением контекста.

Критерий приёмки:

Словарь получает одно слово, перевод — допустимый выбранный фрагмент, а неподдерживаемые действия скрываются.

### Этап 5. Explain

Реализовать:

- Explain из popover.
- Explain из списка исправлений.
- Bottom sheet на мобильном.
- Сохранение существующего интерфейса на desktop.
- Корректную привязку к исправлению.
- Загрузочные, сохранённые и ошибочные состояния.
- Закрытие и восстановление контекста.

Критерий приёмки:

Explain объясняет конкретное изменение, а не случайно выделенное слово, и не создаёт лишних запросов.

### Этап 6. Интеграция и регрессии

Проверить:

- Полный сценарий Correction.
- Несколько вариантов.
- Strict / Rewrite.
- Разные длины текста.
- Несколько ошибок.

- Корректный контекст Explain.

### 19.3. Explain

Проверить:

- Явный запуск.
- Загрузку.
- Успех.
- Ошибку.
- Повторное открытие сохранённого объяснения.
- Отсутствие повторного API-запроса при простом повторном открытии.
- Закрытие drawer.
- Восстановление контекста.

### 19.4. Ручная визуальная проверка

Проверить минимум:

- Mobile 360 px.
- Mobile 390 px.
- Desktop 1440 px.
- Светлую и тёмную темы, если обе доступны.
- Короткий текст.
- Длинный текст.
- Много исправлений.
- Popover около края экрана.
- Drawer с длинным объяснением.

Не полагаться только на успешную компиляцию.

## 20. Общие критерии приёмки

Работа считается завершённой, если:

- [ ] Correction открывается и работает.
- [ ] Существующая функциональность сохранена.
- [ ] Оригинальная палитра Gramika сохранена.
- [ ] Карточка результата соответствует согласованному дизайну.
- [ ] Высота карточки зависит от содержимого.
- [ ] Навигация вариантов занимает одну компактную строку.
- [ ] Отдельного крупного бейджа Strict нет.
- [ ] Точек пагинации нет.
- [ ] Предыдущие варианты сохраняются.
- [ ] «Ещё вариант» открывает bottom sheet.
- [ ] В bottom sheet есть только Strict/Rewrite.
- [ ] Выбор модели отсутствует.
- [ ] «Новый текст» отделён от «Ещё вариант».
- [ ] Список исправлений работает.
- [ ] Одно слово выделяется корректно.
- [ ] Многословное выделение работает.
- [ ] Контекстное меню показывает только допустимые действия.
- [ ] Dictionary не предлагается для нескольких слов.
- [ ] Translate получает правильный выбранный текст.
- [ ] Explain получает правильный контекст исправления.
- [ ] Explain открывается в drawer.
- [ ] Нет автоматических Explain-запросов.
- [ ] Нет ненужных повторных LLM-запросов.
- [ ] Возврат из инструментов не теряет контекст Correction.
- [ ] Длинные тексты работают корректно.
- [ ] Нет горизонтальной прокрутки и перекрытия элементов.
- [ ] Клавиатурная и touch-навигация работают.
- [ ] Другие страницы приложения не сломаны.
- [ ] Существующие и новые релевантные тесты проходят.

## 22. Правила работы агента

1. Не выполнять все этапы одним большим изменением.
2. Сначала изучить существующий код.
3. Не менять другие страницы.
4. Не выполнять глобальный рефакторинг без необходимости.
5. Не менять backend без согласования.
6. Не менять API и промпты.
7. Не удалять существующие функции ради упрощения интерфейса.
8. Не добавлять новые возможности, которых нет в ТЗ.
9. Не внедрять новые зависимости без обоснования.
10. Не добавлять автоматические повторные запросы.
11. Не копировать цвета из макетов.
12. Не скрывать функциональные регрессии за визуально успешной реализацией.
13. После каждого этапа представлять проверяемый результат.
14. При существенной неопределённости задавать вопрос, а не придумывать новое поведение.

## 24. Итог

Цель работы — создать современный, удобный, mobile-first интерфейс Correction, сохранив всю существующую функциональность Gramika.

В центре UX должны находиться:

1. Чтение и понимание исправленного текста.
2. Простое переключение между вариантами.
3. Понятное создание дополнительных вариантов.
4. Удобная работа с отдельными словами и выражениями.
5. Контекстное объяснение конкретных ошибок.
6. Предсказуемая навигация без потери данных.

**Необходимо получить работающий, протестированный интерфейс, а не только визуальное соответствие макетам.**
